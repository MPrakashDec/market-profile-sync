### Why the Deterministic State Engine is Next:

1. **Law 3 (State-Machine Cooldowns & Trade Caps):**
   - We need explicit states: `AWAITING_OPEN` $\rightarrow$ `IB_BUILDING` $\rightarrow$ `PERIMETER_PROBING` $\rightarrow$ `IN_TRADE` $\rightarrow$ `COOLDOWN_LOCK` (15 min locked after exit) $\rightarrow$ `MAX_TRADES_HALT` (hard stop at 3 trades/session).
   - Currently, if a setup flickers for 3 consecutive 1-second ticks, an indicator might trigger 3 orders. A deterministic FSM makes multi-trigger bugs mathematically impossible.

2. **Strict Invariant Transitions (Zero Race Conditions):**
   - An order can only be generated if the FSM state is strictly `READY_TO_FIRE`.
   - Once filled, state transitions to `POSITION_OPEN` with hard stops:
     - Call: `assert stop < entry < target` (Law 2)
     - Put: `assert stop > entry > target` (Law 2)
   - Exit locks the system into `COOLDOWN` where all signal generation is dead for 15 minutes.

3. **Deterministic State Ledger:**
   - Persisting state transitions to SQLite (`ai_trades.db`) or a single lightweight memory-mapped ledger so if the script or connection restarts at 11:30 AM, it restores its exact position, trade count, and cooldown without amnesia.
