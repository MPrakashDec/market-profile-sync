---

### 🏛️ 1. The Monorepo "Tiered Lifecycle" Standard
Institutional quant desks never leave 200 experimental research scripts in the same folder as live execution code. They strictly separate the codebase into 3 tiers:

```
├── core/ (or engine_v3/)    <-- Tier 1: Production (Strictly audited, 0 dead code, sub-millisecond)
├── research/ (or scratch/)  <-- Tier 2: Active R&D (Probes, temporary backtests)
└── archive/                 <-- Tier 3: Cold Storage (Retired tools, frozen with metadata)
```
- **Why?** Having dead scripts in the active directory causes **Operational Risk** (accidentally importing an old buggy module, IDE slowdowns, and AI context confusion).

---

### 📜 2. The ADR Standard (Architecture Decision Records)
Created by Michael Nygard (used across AWS, Google, and hedge funds), an **ADR** is the formal industry standard for documenting why code was created, changed, or retired.

Every entry follows a strict 4-part schema:
1. **Context:** What problem were we solving? *(e.g., Fyers canvas DOM was failing to provide clean IV/OI)*.
2. **Decision:** What tool did we build? *(e.g., Built `zerodha_edge_scraper`)*.
3. **Status:** `DEPRECATED` $\rightarrow$ `SUPERSEDED BY KITE ENCTOKEN BRIDGE`.
4. **Lineage / Consequence:** What replaced it and why? *(Direct zero-cost HTTP routing with $<50$ms latency replaced the browser extension)*.

---

### 📝 3. The "Keep a Changelog" Standard ([keepachangelog.com](https://keepachangelog.com))
The international standard for tracking changes across dates. Every release or day is categorized under 5 universal tags:
- `Added:` New live engines or HUD modules.
- `Changed:` Upgrades (e.g. Vectorized NumPy Greeks).
- `Deprecated:` Modules slated for retirement.
- `Archived / Removed:` What was moved to cold storage and where.
